# CanopusConnect 协议消融实验

状态：已运行 host 接收热路径原型、故障注入及传输模型。没有运行真机蓝牙传输，也没有实现完整设备安装器。本报告用于选择协议参数，不能作为手环实测性能报告。

## 1. 产物与复现

- [C 接收原型](../../tests/protocol/canopusconnect_bench.c)：实际二进制头处理、固定缓冲、POSIX 文件写入、sync、SHA 回读及流式 inflate。
- [实验驱动](../../scripts/bench-canopusconnect.py)：生成固定种子的 ZIP，构建原型，运行矩阵与故障检查，输出完整数据。
- [原始结果](canopusconnect-ablation.json)：各次运行计数、host 时间、对象大小、假设和模型结果。
- [精简协议](../canopusconnect_proto.md)与[两端方案](../canopusconnect_implementation.md)。

```sh
python3 scripts/bench-canopusconnect.py --repeats 3
```

需要 C 编译器、系统 zlib，以及相邻 Canopus-Private 的 `third_party/sha256` 和 C SDK 头文件；可用 `CANOPUS_ROOT` 指定位置。没有网络依赖。临时包和可执行文件自动清理，结果文件保留。

本次环境为 Darwin arm64、Apple clang 21、Python 3.15。CPU、文件系统和闪存控制器与手环不同。每组测 3 次，host 时间取中位数；帧数、显式对象大小与 I/O 次数是确定性计数。

## 2. 实验边界

分为三类，不能混用数字：

1. **host 实际执行**：C 接收状态、数据拷贝、pwrite / pread / fsync 调用、SHA 内容比较；zlib 用自定义 allocator 测其解码 heap 峰值；ASan / UBSan 检查原型。
2. **串行成本模型**：用测得帧数 / I/O 次数，加指定的 RPC、事件、带宽和 I/O 延迟，比较单因素变化。它是加和模型，不模拟完整蓝牙调度。
3. **窗口离散事件模型**：有序上行、FIFO owner、4 槽 RX、4 槽 RPC TX、2 槽事件 TX、RPC 响应优先、有限业务额度。模拟多个 RPC 在途的条件收益与容量违例，不执行真实 AstroBox / 固件。

原型不是从不存在的生产实现中抽出的对照组。A0 是按初稿热路径构造的参考实现，仅包含 32 字节头、逐片 JSON 回执、逐片写和 64 KiB 检查点。它不解析完整控制 JSON，也不包含初稿的 1 秒同步定时器；后者单独建模。不能据这些结果声称已经测出初稿整个管理器的 RAM 或 CPU。

实际文件系统库、固件队列、调用栈、分配器元数据、原生界面和完整 manifest / ZIP 目录解析不计入 C 显式对象大小。fsync 调用成功也不是实际掉电恢复证明。现有 SHA 源码的 signed-shift 写法未在本轮改动；它以 ASan 编译，新增原型使用 ASan + UBSan。

## 3. 数据集

输入为实际生成的 Deflate ZIP，根目录含 CRPack v1 manifest。`.bin` 只是合成传输数据，不是已验证的设备 LVGL 图片。

| 数据集 | 普通文件数 | ZIP 字节 | 实际解压字节 | 用途 |
| --- | ---: | ---: | ---: | --- |
| entropy-1m | 65 | 1,055,810 | 1,048,733 | 低压缩率，观察链路和写盘热路径。 |
| compressible-1m | 65 | 11,765 | 1,048,733 | 高压缩率，检查小包开销。 |
| many-files-1m | 2,049 | 1,272,064 | 1,048,733 | 大量小文件，观察 ZIP 容器开销。 |

SHA、固定 ZIP 时间戳、随机种子记录于驱动和原始 JSON。上传处理的是 ZIP 字节，包内文件数不会增加接收位图或传输状态表；解压阶段仍需要独立处理文件清单。

## 4. 顺序消融：帧头、ACK、缓冲与检查点

以下使用 entropy-1m。A0 → A5 每步只改一个因素；B 组在 A5 基础上比较检查点和恢复成本。二进制回执为 20 字节，包括 12 字节头和 8 字节进度。

串行成本模型的默认假设：每个 RPC 20 ms、每个业务事件 10 ms、应用字节带宽 128 KiB/s、每次写调用 0.2 ms、每次 sync 5 ms。不猜测 WearPacket、加密与 CPC2 的完整外层字节；它们的固定开销主要归入 RPC 假设。速度不包含安装、解压和磁盘 SHA 阶段。

| 变体 | 本步变化 | DATA 帧 | 业务事件 | 数据写调用 | sync 调用 | 模型 KiB/s |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| A0 | 初稿参考 | 2,357 | 2,357 | 2,357 | 34 | 12.61 |
| A1 | 头 32 → 12 字节 | 2,257 | 2,257 | 2,257 | 34 | 13.22 |
| A2 | JSON → 二进制 ACK | 2,257 | 2,257 | 2,257 | 34 | 13.40 |
| A3 | 每 4 片 QUERY 一次累计结果 | 2,257 | 565 | 2,257 | 34 | 14.50 |
| A4 | 每 8 片 QUERY 一次 | 2,257 | 283 | 2,257 | 34 | 16.47 |
| A5 | 加 4 KiB 合并写缓冲 | 2,257 | 283 | 283 | 32 | 16.58 |
| B1 | 检查点 64 → 256 KiB | 2,257 | 283 | 283 | 8 | 16.61 |
| B2 | B1 改每 16 片 QUERY | 2,257 | 142 | 283 | 8 | 17.84 |
| B3 | A5 取消周期检查点，仅最终同步 | 2,257 | 283 | 283 | 2 | 16.62 |
| B4 | B1 取消磁盘 SHA | 2,257 | 283 | 283 | 8 | 16.61 |
| C0 | 64 KiB 检查点、每 4 片主动累计 ACK、合并写 | 2,257 | 565 | 565 | 32 | 17.35 |

A3 / A4 的 QUERY 是额外 RPC，已计成本；它们只作为便于隔离因素的对照方案。最终协议采用 C0 的主动累计 ACK，QUERY 留给异常恢复，避免每组都增加一个请求。C0 同时改变了确认触发方式和组合参数，因此属于最终候选配置，不声称是单因素消融。

结论：

- 12 字节头增加每帧有效数据 20 字节，DATA 数减少约 4.2%；保留。
- 去掉逐片 JSON 主要减少业务字节和格式化工作；控制消息解析的完整 CPU 收益本实验没有测。
- 每 8 片合并写可把 2,357 次数据写降到 283 次；最终每 4 片 ACK 配置为 565 次，仍减少约 76%，并更早归还滑动窗口额度。
- 256 KiB 检查点和不做周期检查点的吞吐收益都很小，不能只为表中最后一点速度牺牲恢复成本。
- B4 的上传模型速度不变，因为磁盘 SHA 是上传后的独立阶段；取消它减少一次磁盘回读，但会丢失完整压缩包身份校验，见 §8。

其他数据集也按全部变体执行。最终 C0 中，compressible-1m 为 26 个 DATA、7 次数据写；many-files-1m 为 2,719 个 DATA、680 次数据写。小文件多并不增加每片状态，但会增加压缩包本身的目录和头开销。

### 反例：分组 QUERY 并非永远更快

B1 相对 A0，在 RPC / 事件分别为 5 / 2、20 / 10、80 / 40 ms 的模型下，吞吐分别增加约 27.1%、31.8%、31.8%。但在 RPC 80 ms、事件只有 2 ms 时，额外 QUERY 反而使吞吐下降约 3.7%。

因此不能从一种 RTT 比例就得出“减少 ACK 一定更快”；最终选择主动累计 ACK。实际事件合并和丢失恢复仍需两端实现验证。

## 5. 滑动窗口：当前代码限制与条件收益

核实代码后，CPC2 已有多个 request_id waiter；当前串行主要来自 Connect 层跨 RPC 持有的 connect_lock。**窗口可以实现，但需要手机端有界许可和设备队列背压，不能只删锁。**

窗口模型使用当前设备 owner 10 ms、BT 有工作 2 ms / 空闲 10 ms，假设传播 RTT 20 ms、应用上行带宽 128 KiB/s，单个 RPC 返回 32 字节、一次 flush 0.2 ms。包含实际队列容量和响应优先级，不包含 fsync、完整上下行线速竞争、蓝牙重传或真实固件 CPU 时间。

固定业务窗口 8 帧：

| RPC 在途 | 每 8 片 ACK：模型 KiB/s | 每 4 片 ACK：模型 KiB/s | 容量检查 |
| ---: | ---: | ---: | --- |
| 1 | 11.42 | 11.42 | 通过。 |
| 2 | 21.49 | 22.83 | 通过。 |
| 3 | 28.09 | 34.23 | 通过。 |
| 4 | 33.19 | 45.63 | 该单任务场景通过，但没有为其他控制请求预留许可。 |
| 8 | 不作为有效结果 | 不作为有效结果 | RX 峰值 6，超过 4 槽。 |

同一窗口模型内可以比较上述数字，不能用它们直接除以 §4 加和模型速度来宣称提速倍数。没有修改 core / Supervisor，因此它们是待实现的条件收益。

选择默认 2 RPC、验证后最多 3，业务窗口 8、每 4 片 ACK。32 KiB 等更大应用窗口没有证据值得作为首版常驻缓冲；窗口增大也不能绕过 owner 每 tick 一条的处理上限。

额外的调度消融：固定 3 RPC、8 帧业务窗口、每 4 片 ACK，owner 10 / 5 / 2 ms 对应约 34.23 / 45.64 / 45.64 KiB/s。这说明瓶颈转移后继续提高 owner 频率也不一定有收益。5 / 2 ms 是假设中的固件改动，不能算到窗口优化本身。

## 6. 内存：上传固定，解压另算

C 原型没有按 ZIP 大小、帧数或文件数分配接收内存。显式拥有对象：

| 对象 | host sizeof |
| --- | ---: |
| 接收状态，含 4 KiB 数据区 | 4,156 字节 |
| 一帧及复用的短回执 / SHA 上下文区 | 608 字节 |
| 合计 | 4,764 字节 |

SHA 回读直接复用已经排空的上传数据区，没有再放一个 4 KiB 读缓冲。这个大小在所有包和变体中相同；实验没有证明初稿的实际对象一定比它大。完整 OPEN / 持久化元数据、ARM 栈峰值和设备文件系统开销还要在生产实现中测量。

真正的内存大头是 Deflate。用系统 zlib 的真实 raw-Deflate 解码和跟踪 allocator，对 64 KiB、1 MiB、8 MiB 输出分别测得：

| 输出大小 | codec heap 峰值 + I/O 数组 + z_stream |
| ---: | ---: |
| 64 KiB | 45,160 字节 |
| 1 MiB | 45,160 字节 |
| 8 MiB | 45,160 字节 |

这里使用 1 KiB 输入和 4 KiB 输出缓冲。跟踪值不包含 malloc 元数据和调用栈；对象大小依 host zlib 而定。它只说明流式 inflate 的工作内存可不随输出总量增长，尚未选择最终嵌入式解码器，也没有测完整 ZIP reader 或 manifest parser。

因此明确分阶段预算：上传 / SHA 工作区复用，结束后再分配解压工作区；不要在“接收中”就常驻两套缓冲和 32 KiB 历史窗口。

另做历史窗口消融：将 30,000 字节固定随机前缀重复 4 次，生成一个合法原始 Deflate 流。实际 C / zlib 解码在 32 KiB 历史窗口下完整输出 120,000 字节，改成 8 KiB 后解码失败。完整 Deflate 的历史距离可达 32 KiB，不能为了宣称低内存偷偷拒绝正常旧包或改用错误的小窗口。该失败样例和两次解码结果也保存在原始 JSON。

## 7. 检查点与重启重传

对 8 MiB 上传，在确定性组边界时间模型下计算重启重发前缀：

| 策略 | 检查点次数，含最终 | 最大重传字节 | 均匀时刻重启的平均重传字节 |
| --- | ---: | ---: | ---: |
| 每 64 KiB | 125 | 67,392 | 约 33,628 |
| 每 256 KiB | 32 | 265,824 | 约 131,874 |
| 仅完成时 | 1 | 8,388,608 | 约 4,194,561 |
| 64 KiB 或 1 秒先到 | 374 | 22,464 | 约 11,224 |

阈值按一批完整数据写入后检查，因此上界可略超阈值。每个检查点包括数据 sync 和状态 sync 两次，表中次数不等于 sync 系统调用次数。时间模型为串行 RPC 20 ms、每组 QUERY + 事件，不含 I/O；实际窗口化速度会改变“1 秒”策略的行为。

默认保留 64 KiB 字节阈值，取消 1 秒触发。256 KiB 和无周期检查点不作为默认。需要更低掉电损失的设备可以保留时间阈值，但应单独测量，不把它当免费可靠性。

## 8. 故障实验与没有删掉的机制

新增 C 原型以 ASan / UBSan 跑过 10 类有断言检查的场景：累计 QUERY 回执丢失后的重复查询与重复 DATA、偏移缺口、错误任务 token、短帧、缺片后的后缀重传、37 字节短写、重启丢弃未检查点进度、部分写失败后的错误锁存、超额发送时缓冲仍有界、落盘字节被改后的 SHA 不匹配。

这组原型没有完整的租约轮换、生产 RPC waiter、manifest / ZIP 安全解析或注册表恢复，不能宣称完整协议已经通过全部故障场景。那些必须在两端实现后继续验证。

另用实际 ZIP 测试“移除整包 SHA，只保留文件 CRC”的消融：修改 ZIP 注释一个字节，所有文件 CRC 依然通过，但原始包 SHA 改变。它不是资源内容损坏的示例，却准确说明文件 CRC 不能证明“续传的是同一个原始压缩包”。所以保留磁盘 SHA，不逐片额外做 SHA / CRC 或回读比较。

事件丢失模型使用固定种子，在 283 组结果中丢 1 次 ACK；重新 QUERY 可查询累计偏移，假设第二次查询成功时无需重发 DATA。原来 8 秒业务等待会额外空等 8 秒，这也是精简协议将普通 ACK 查询等待建议改为 1 秒的原因。该模型只有每组一次可能丢失，不是任意连续丢包证明。

## 9. 最终选择与仍需实机回答的问题

精简后的默认组合是 **12 字节头、二进制消息、2 个 RPC 在途、最多验证到 3、8 帧字节额度、每 4 片累计 ACK、4 KiB 数据区、64 KiB 检查点、最终磁盘 SHA**。LIST 改为有 revision 的单条固定格式分页，最坏整帧 422 字节，不再生成大 JSON 快照或列表哈希。

保留了内容身份、断点恢复、错误锁存、租约失效、活动资源保护和安全安装。删除的是逐片重复元数据、逐片业务回执、大列表快照和不必要的定时同步。

后续必须真实测量：手机各平台并发入队顺序和发送时序、设备 flash 写入 / sync 延迟、两端总队列峰值、ACK 饥饿、共享管理 RPC 的响应、息屏持续调度、ARM 内存 / 栈峰值、完整解压及登记恢复。当前所有实验产物都不修改生产传输代码。
